# Explicit manuscript discrepancies and engineering decisions

The user-supplied manuscript is the design source. It is a 31-page document ending at Section 5.1, not a complete experimental result archive. This file records deviations rather than presenting inferred equations as verified originals.

1. **Abstract vs Section 4.1 latency:** 166.05 ms and 17.05 ms are inconsistent. Code reports independently measured values and separates crypto service, Python receiver processing and modelled/radio arrival delay.
2. **Rate-control arithmetic:** the paper references ~190 requests per second for 200 vehicles; one escalation per pseudonym every 2s caps admitted requests from 200 independently signed pseudonyms at 100/s. Code counts *attempted* and *admitted* separately and reports sheds.
3. **L0 acceptance of current abnormal packet:** pure EWMA risk can transiently permit a single grossly impossible signed packet while long-term trust remains high. To avoid forwarding positively anomalous messages, the code **adds a conservative immediate minimum L2 floor when the current behavioural score is below 0.5**, or a current kinematic plausibility/trajectory-consistency feature is below 0.3. Uncorroborated event messages also receive a minimum L2 floor. This is a research safety guard that is not separately enumerated in Algorithm 3's original hard-rule list. Evaluate its effect explicitly in any faithful reproduction.
4. **Raw feature normalisation incomplete:** original numeric normalisation bounds are not all supplied. Code uses explicit interpretable rules: 10Hz expected rate with PDR compensation, gap-normalised timing jitter, 60m/s speed, 9m/s² acceleration, 1rad/s yaw, and first-order trajectory residual. These choices are documented and configurable. All 5 group weights equal Table 3; NO calibration fitting on the test set.
5. **Context stress normalisation:** default density saturation is 200 vehicles; alert saturation is 20 alerts per window. Exact normalisers were absent from the text-only source. Both settings are configurable.
6. **Pseudonym cryptography:** the paper uses P-256 signing and ECDH with same static pseudonym key. This research prototype reproduces that step; standard security guidance recommends cryptographic key separation and independently validated key exchange for deployment.
7. **Mean 166-byte packet overhead:** ECDSA raw signatures are 64 B, but prototype packets are canonical JSON (larger). No IEEE 1609.2 ASN.1 packed encoder, 1609.2 certification or exact protocol byte-size replication is claimed.
8. **Trust-token transfer:** RSU-signed pseudonym-bound tokens can initialise trust at another authenticated RSU, but do not create untraceable multi-RSU cross-pseudonym linking. New pseudonyms require new TA-certified credentials and an authenticated reissue.
9. **Formal proof:** manuscript refers to ProVerif and ROM; it contains no model or proof output in the provided 31 pages. Runtime tests are not a substitute for a ProVerif execution or ROM reduction. These proof results are not reproduced.
10. **External baselines:** multi-tier and dynamic trust are controlled periodic-trust *approximations*. Claims of reproducing the cited papers' exact algorithms require independent review of source methods.
11. **Data roles:** CAN frames never leave internal vehicle networks; offline CAN timing profiles inform adversarial beacon timing only. VeReMi lacks native ECDSA credentials; synthetic signing creates a measurable cryptographic overlay that is distinguishable from original ground truth.
12. **SUMO+NS3:** Python FCD conversion and RX import were tested on sample files; native ns-3 C++ sidecar requires compilation and external simulation. No claim of a completed, fully compliant, real-time TraCI/WSMP/IEEE1609.2 implementation is made.
13. **Benchmark ground truth:** `accuracy = (TP+TN)/all`, as the paper defines ASR via confusion matrix. Here TP/FP positive class is **legitimate accepted**, and a HOLD is counted as not admitted. Other studies sometimes define ASR as genuine-message acceptance; do not compare without harmonising definitions.
14. **Beacon rate inconsistency:** Section 3.1.1 mentions 'once every 2 seconds (10Hz)', an impossible combination. Table 3 and Section 5 use 100ms / 10Hz; code uses 10Hz.
15. **Security claims:** Sybil identifiers with valid independent TA-issued pseudonyms cannot all be detected by signature verification alone. The present prototype can identify implausible Sybil behaviour, not prove complete Sybil resistance for all pseudonym patterns.
